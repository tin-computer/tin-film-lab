# Lessons from film trials

Read this with FILM_FLOW.md before asking questions. These are working rules from user feedback and saved film reviews, not a claim that model training changed. Product choices, music taste and approvals stay with their owner and brief.

## Questions people can answer

28 Oct delivery feedback: repeated suggestions around 20 seconds and optional format questions limited the films. Keep an explicit delivery question in each new interactive brief; suggest length from the story and confirm frame shape with the user. The instructions have changed; a fresh onboarding and render trial is still needed to check the resulting behaviour.

Start with the current product's action and the viewer's reason to care. An archive is optional research for the agent. Do not ask the user to pick an archive video or recognise a source brand, number, filename or storytelling term.

If a choice would change the story, describe what happens on screen and what the viewer understands. For example, replace “Krea ref 011 structure” with “We follow one table as a new column fills, then see the report use that column”, only when the product evidence supports that action. The option must work without opening a reference. Offer a source link and a short explanation only when the user wants to compare references.

Make candidate ideas from the product before searching. When comparing alternatives, include an idea that does not start from an archive film. They must differ in events, viewpoint or discovery, not only texture or music. Do not require stock footage, an old-film montage, a mascot, a twist or a problem/settings/result sequence. A direct demonstration can be the strongest idea. Choose for this brief, not for novelty alone.

Keep source IDs, useful intervals and adaptations in STORY.md. Write the observed action in plain words beside the source so it remains useful without the original video. If the archive is unavailable, use product evidence and these general lessons. Do not pretend that private Desktop files are present in a customer's sandbox.

## Keep learning from each trial

In the film's existing REVIEW.md keep a short row: `feedback/source | scene or question | change | observed result | still open`. Record an onboarding problem even if no render followed it. Apply the change to a named question or scene, then check the next question or rendered result. “Instruction updated” and “result improved” are separate states.

Read relevant unresolved rows before the next revision. Add a general lesson here only when the feedback supports it; keep personal taste and product facts in that film's brief or owner notes. Preserve the original comment and scope. If a preference changes, record what superseded it instead of silently rewriting history. Never describe an agent check as Hamit's review or an unfamiliar-viewer test.

Before delivering the workflow to another user, try it with only its packaged instructions, that user's product sources and available tools. Questions must make sense with no private reference archive. Until that trial is run, portability and one-shot quality remain unverified.
